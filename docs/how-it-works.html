Bracket 10 — How It Works

A self-hostable March basketball bracket pool. This guide walks through how the system is built and how data flows through it — from a fan submitting picks to ESPN scores landing on the leaderboard automatically.

Node.js + Express Google Cloud Firestore Cloud Run EJS / PWA Cloud Scheduler ~$0/month off-season
The Big Picture

What this system is

Run a March bracket pool with your friends — without a spreadsheet.

Bracket 10 is a web application that lets a group of people pick which teams they think will go furthest in a single-elimination basketball tournament, then automatically tracks scores and ranks everyone on a live leaderboard. It's designed to be self-hosted: one person deploys their own copy for their friend group, and Google Cloud's free tier covers most pools at roughly $0/month outside of tournament weekends.

Unlike a traditional 63-pick bracket, each participant picks exactly 10 teams. Points accrue every time one of your teams wins a game, weighted so that later-round wins are worth dramatically more. The whole experience is delivered as a Progressive Web App (PWA) so it installs and caches like a native app on phones.

The four things it does

📝

Public entry & self-service edits

Anyone with a link picks 10 teams, gets a confirmation, and can edit during the registration window — either via Entry ID + email or by signing in with Google.

🛠️

Admin dashboard

A Google-authenticated admin sets up the tournament bracket, manages entries/teams/groups, records results manually, and watches cloud spend.

📡

Live ESPN score polling

During the tournament a scheduled job pulls completed-game scores from ESPN every 15 minutes and updates winners + points with no human in the loop.

🏆

Leaderboard & projections

A live standings grid shows current points and maximum possible points so participants can see who's still mathematically in it.

How it's built (the shape of the code)

The codebase follows a strict MVC layering. A request always flows down the stack, and only the bottom layer is allowed to touch the database. This makes the business logic reusable: the same services power both the website and the automated polling job.

Requests flow strictly downward; only repositories talk to Firestore.
Two entry points, one shared core. The server.js Express app handles all human traffic, while jobs/espn-poll.js runs as a scheduled Cloud Run Job that bypasses Express entirely. Both call the same services and repositories and write to the same Firestore — so game results have two writers that share the same core logic.

System architecture

What talks to what — the layers, the cross-cutting modules, and the external systems.

The system has two runtime processes that share one code core. The web app is a Cloud Run service; the poll job is a separate Cloud Run Job. Both depend on the same services and repositories, and both read and write the same Firestore database. Why two writers matter. Both the admin manual path and the ESPN poll call gameService.updateTeamRecords, but they use different points-recalculation strategies: the admin click does a full-year recalc of every entry, while the poll does a targeted recalc of only entries that picked an affected team. They converge to the same answer; the poll is just cheaper. See the Data Flows tab for both traces.

Flow 1 — A fan creates an entry Public

The public registration flow. Note the ordering safeguard: the confirmation token is staged in the session before the database write, so a save failure can never produce a duplicate entry on retry. No picks or PII ever travel through query parameters.

Entry creation — validation, ordering safeguard, and automatic cache invalidation.

Self-service edits come in two flavors, both funneling into one shared applyEntryUpdate helper so the write logic can't drift:

  • Path A /my-entry — verify with Entry ID + email; a Firestore-backed limiter (10/10 min, keyed by entry ID) blocks email brute-force even across rotating IPs.
  • Path B /my-brackets — sign in with Google; see all your entries across every year, edit the current one. Ownership is re-checked against the stored entry on every write (IDOR-proof).

In both paths, server-owned fields (email, groups, payment, email-sent metadata) are always taken from the stored entry, never from form input.

Flow 2 — Admin records a result manually Admin

The manual scoring path. Recording a winner advances them into the next game (inside a Firestore transaction), updates both teams' record docs, then does a full-year points recalc and clears all caches.

Manual scoring — transactional advancement + full-year recalc. /undoGame is the mirror image.

Flow 3 — Automated ESPN polling Poll job

The production score-update path does not go through Express at all. Cloud Scheduler triggers a Cloud Run Job via IAM/OAuth — there's no shared secret and no web endpoint. The job matches ESPN's completed games against unresolved DB games, applies winners in parallel, then runs a targeted recalc touching only affected entries.

ESPN polling — IAM-authenticated, parallel resolution, targeted recalc. No Express, no shared secret.
Idempotency by design. On resolution the winner field is written last — it's the commit marker. A mid-resolution failure leaves the game unresolved, and the next poll cycle simply retries every step. On undo it's cleared last, so a mid-undo failure leaves the game resolved and the admin can retry safely.
Firestore Schema

Database

Google Cloud Firestore — a serverless NoSQL document store, used as the single source of truth.

Data is organized in a hierarchical structure (the current default): everything tournament-specific lives under a tournaments/{year} document, with games, entries, regions, and school records as subcollections. Reference data that spans all years — schools, conferences, groups — lives in top-level collections. A legacy flat structure (year-as-a-field in top-level collections) is still supported behind a config flag.

Why hierarchical? No where('year','==',…) filters are ever needed, getTournamentTeams becomes a single subcollection read instead of a 3-way join, and the game-view render needs no joins at all — school records are fully denormalized at setup time.

Three query-optimization patterns

The repository layer enforces three patterns to keep DB cost low and avoid race conditions under heavy load:

♻️

Cached reference reads

Bulk/setup methods never call collection('school').get() directly — they go through _getCached* helpers sharing 24h cache keys, so a warmed cache means zero DB reads.

🔒

Atomic transactions

Any read-then-write (advancing a winner, updating points) uses db.runTransaction so concurrent poll resolutions can't race. Cache invalidation is gated on whether the write actually happened.

✂️

array-contains-any chunking

Firestore caps array-contains-any at 30 disjuncts. Queries over an unbounded team-ID list chunk into batches of 30, fire in parallel, then dedupe by entry ID.

The points system

Points are cumulative and awarded for winning a game (advancing), not for reaching a round. The weighting roughly doubles each round, so the championship game alone is worth more than the entire first round.

RoundTeamsPoints for a winround int
First Four68 → 6400
Round of 6464 → 3221
Round of 3232 → 1632
Sweet 1616 → 853
Elite Eight8 → 494
Final Four4 → 2175
Championship2 → 1336
First Four lifecycle. A First Four matchup is picked as one combined option ("Team A / Team B"), worth 0 points. When the play-in game resolves, every entry holding that slot is auto-swapped to the winner. Picks are normalized against live game state at write time, so a user always ends up holding whoever actually advanced.

Backups & seeding

  • Backup: node scripts/backup-db.mjs exports every collection to timestamped NDJSON in /databasebackup/. Email fields are blanked in all exports.
  • Restore: node scripts/restore-db.mjs (supports --dry-run, --only=<collection>).
  • Local seed: node scripts/seed-emulator.mjs loads ~360+ D-I schools, conferences, mock groups, PII-free mock entries, and the 2022 bracket into the Firestore emulator.
Automated Scores

ESPN score polling

Game results update themselves via ESPN's free, unauthenticated scoreboard API.

During the tournament, two Cloud Scheduler jobs fire every 15 minutes within active game windows. Each fires a Cloud Run Job (authenticated by IAM, no shared secret) that runs jobs/espn-poll.js — a process completely separate from the web app, but reusing the same services and repositories.

The poll pipeline — scheduler → job → match → write → targeted recalc → Firestore.

The scheduler jobs

JobSchedule (cron)Window (ET)
espn-poll-day*/15 17-23 * 3-4 0,4,5,6Thu–Sun, 5 PM – midnight
espn-poll-night*/15 0-1 * 3-4 0,1,5,6Fri–Mon, midnight – 2 AM
Cost note: these jobs are a source of Cloud Run egress cost. They're scoped tightly to March–April game windows and should be disabled or slowed when the tournament isn't active.

Manual hold — undo vs. the poll

ESPN's "today + yesterday" feed keeps listing a completed game for ~48 hours. So when an admin undoes a result, the code sets manualHold: true in the same write that clears the winner. The poll skips held games — otherwise it would simply re-resolve the undone game within one cycle. The hold clears when a result is recorded, or via the Release Hold button (POST /releaseGameHold).

Team-name mapping

ESPN identifies teams by displayName (e.g. "Duke Blue Devils" = nameNick + mascot). A static src/config/espnTeamMap.json maps those strings to internal sID values. scripts/buildEspnMap.js auto-matches against the DB; any null entries must be resolved by hand before the tournament starts. Unmapped names at poll time are reported and skipped rather than guessed.

The job artifact

The poll image is kept tiny via a two-stage Docker build (Dockerfile.poll): esbuild bundles jobs/espn-poll.js plus the full src/ import tree into a single dist/poll.mjs (~4.3 MB), and the production stage copies only that file into a distroless image — no node_modules at all.

Dry-run for admins. POST /admin/trigger-espn-poll runs runEspnPoll(year, {dryRun:true}) — it previews what would change without writing anything. It's a console convenience; the real scheduled job never authenticates through the web app.
Performance

Caching

A tiny in-process TTL cache keeps Firestore reads — and therefore cost — low.

cacheUtils.js is a hand-rolled Map-based cache (it used to depend on node-cache) storing { value, expiresAt }, lazily pruning expired keys and tracking hit/miss stats. Default TTL is 30 minutes; static reference data uses a 24-hour TTL.

Instance-local. The cache lives in process memory, so it fragments if Cloud Run scales to multiple instances. That's an accepted trade-off — correctness comes from repository-driven invalidation, and each instance independently warms its own cache.

Read-through with automatic invalidation

Repositories own invalidation: writes bust the relevant cache keys automatically, so reads can't go stale.

Invalidation rules

  • After game writes — the repo auto-invalidates activeGames_, activeFutureGames_, tournamentDetails_, and gameViewData_{year}_*.
  • After entry writes — the repo auto-invalidates groupTeams_, entriesForGroup_, allEntries_.
  • After batch points writes (the poll path) — busts the standings caches too, which is what keeps the leaderboard fresh after auto-recorded scores without a full cache nuke.
  • clearAllCache() is the broad nuke — used only after full point recalcs or a tournament reset. Never call it before reads.
Cross-class cache sharing. The repository's private _getCachedSchools / _getCachedConferences / _getCachedRegions helpers share the same cache keys as the public getAll* methods — so an already-warmed cache is reused for free when denormalizing school records, instead of re-fetching.
Defense in Depth

Security

Layered protections, mostly hand-rolled and dependency-free, in the same spirit as the rest of the stack.

Authentication — three independent identities

🛡️

Site admin

Google OAuth + an ADMIN_EMAILS allowlist. ID token verified with an audience pin. Sets siteAdmin; guarded by requireSiteAdmin. 8-hour session (30 days with remember-me).

👤

Participant

Any verified Google email → "My Brackets". Sets only userEmail (never siteAdmin); guarded by requireUser. 14-day cookie. Strictly weaker than admin.

🔑

Entry owner

Lightweight self-service: Entry ID + matching email sets a year:entryId session key. Anti-enumeration: identical error for bad ID vs bad email.

Session fixation defense. req.session.regenerate() is called at every privilege transition — before setting any flag that grants access — so a pre-set victim cookie can't be reused after they authenticate. Sessions persist in Firestore (express-sessions), surviving Cloud Run restarts, and are TTL-reaped.

Content Security Policy — strict nonce

Helmet was removed in favor of a custom securityHeaders middleware. The enforcing script-src is 'self' 'nonce-<per-request>' 'strict-dynamic' https: — with no 'unsafe-inline'. Every first-party <script> must carry a per-request nonce or it's blocked. Inline on*= event-handler attributes are blocked entirely (script-src-attr is dropped); listeners use a delegated dispatcher instead. A mirrored report-only header feeds POST /csp-report as a regression early-warning channel.

Rate limiting — two backends

LimiterBackendLimitUsed on
LoginFirestore (global)15 / 10 min per IPOAuth start + callback
VerifyFirestore (global)10 / 10 min per entry ID/my-entry/verify
PublicIn-memory (per instance)30 / min per IPpublic POST routes

Security-sensitive routes use the Firestore-backed limiter so the cap is global across instances; high-volume public reads use the cheap in-memory one. Keying verify on entry ID blocks email brute-force even when an attacker rotates IPs. The Firestore limiter fails open on store errors (an outage must not lock people out of login) and bounds writes to stay inside the free tier.

Other hardening

CSRF on every admin POST

A per-session synchronizer token guards every requireSiteAdmin POST route — minted only for admin sessions, so anonymous traffic stays write-free. A test fails if an admin POST is registered without the guard.

CSV formula-injection defense

The public CSV export prefixes any cell starting with = + - @ etc. with a quote, neutralizing =HYPERLINK(...)-style spreadsheet formulas (OWASP defense), independent of RFC-4180 quoting.

Safe DOM construction

Client scripts build nodes with createElement + textContent, never by concatenating into innerHTML — closing the XSS sink where one missed escape re-opens the hole.

Generic error responses

In production, DatabaseError / ServiceError payloads are generic; full detail stays in server logs. PII fields are redacted in start-logs.

Preserve these invariants. OAuth validates a session-backed state before exchanging the code. Public entry edits are keyed by year:entryId, re-read the stored entry, and preserve server-owned fields. These are the load-bearing security guarantees of the app.

Deployment

Push to main → Cloud Build → Cloud Run. Scales to zero when idle.

The app runs on Google Cloud Run, deployed automatically when a commit lands on main via Cloud Build. Because Cloud Run scales to zero, the app costs essentially nothing when no one is using it — the whole architecture is designed around a $0/month off-season cost contract.
